## 1. Введение

### 1.1 Цель работы

Цель работы — получить практический опыт применения алгоритмов поиска в таблицах данных, хранящихся в файле, и сравнить линейный поиск с поиском Фибоначчи при использовании дополнительного индекса в оперативной памяти.

### 1.2 Постановка задачи и вариант

В соответствии с вариантом 4 требуется хранить сведения об автомобилях и владельцах. Ключ записи — **номер автомобиля**. Требуется создать файл записей с уникальными ключами, реализовать линейный поиск непосредственно в бинарном файле, а также организовать индекс в памяти «ключ — смещение записи в файле» и выполнять поиск по индексу алгоритмом Фибоначчи. Для размеров файла 100, 1 000 и 10 000 записей необходимо провести замеры и сопоставить результаты.

Пользовательская структура проекта сохранена под именем `siaod/pr_1`. Номер практической работы в отчёте соответствует приложенному условию (№ 5); `pr_1` — имя каталога, заданное для первой практической работы в структуре репозитория.

### 1.3 Средства разработки

Программы написаны на C++17 без сторонних C++-библиотек. Сборка организована через CMake, поэтому исходники можно собирать на Linux и Windows при наличии компилятора C++17 и CMake. Для обработки результатов применяются Python 3, pandas и matplotlib. Все три программы работают в терминале.

## 2. Задание 1. Формирование бинарного файла

### 2.1 Постановка задачи

Необходимо создать записи варианта 4, присвоить каждой записи уникальный псевдослучайный ключ, сохранить данные в текстовом файле и преобразовать их в бинарный файл фиксированных записей. Для демонстрации и проверки используется набор из 100 записей.

### 2.2 Структура записи и прямой доступ

Номер хранится как строка длиной 8 символов, например `A123BC77`. Используются латинские начертания букв, соответствующие допустимым буквам российского регистрационного номера. Марка и сведения о владельце хранятся в UTF-8. Внутри полей не используется разделитель `|`, поэтому текстовая запись имеет однозначный формат `номер|марка|сведения о владельце`.

**Таблица 1 — Поля бинарной записи автомобиля варианта 4 и занимаемый ими размер.**

| Поле | Представление | Размер поля в бинарной записи |
|---|---|---:|
| Номер автомобиля (ключ) | `char[9]`: 8 символов номера и завершающий `\0` | 9 байт |
| Марка автомобиля | `char[48]`, UTF-8, остаток поля заполняется нулями | 48 байт |
| Сведения о владельце | `char[96]`, UTF-8, остаток поля заполняется нулями | 96 байт |
| **Итого** | Фиксированная структура `CarRecord` | **153 байта** |

Структура содержит только массивы `char`, поэтому для неё не возникает межполевого выравнивания; это дополнительно проверяется директивой `static_assert(sizeof(CarRecord) == 153)`. Записи сериализуются в файл последовательно, в исходном порядке. Для записи с индексом `i`, где нумерация начинается с нуля, начальное смещение равно

```text
offset(i) = i × sizeof(CarRecord) = i × 153 байта.
```

Для прямого доступа программа устанавливает позицию чтения методом `std::ifstream::seekg`, затем считывает одну структуру через `read`. Запись не содержит целочисленных полей, поэтому байтовый формат не зависит от порядка байтов процессора. Формат рассчитан на чтение тем же описанием `CarRecord`; произвольные внешние файлы другой структуры программа не интерпретирует.

## 3. Задание 2. Линейный поиск в бинарном файле

### 3.1 Постановка задачи и алгоритм

Требуется найти запись с заданным номером автомобиля, просматривая бинарный файл от начала до конца. Записи не отсортированы по номеру: порядок в файле соответствует порядку генерации. Поэтому линейный поиск не требует предварительной сортировки и может найти совпадение в любой позиции.

Псевдокод линейного поиска:

```text
ЛИНЕЙНЫЙ_ПОИСК(файл, ключ):
    для i от 0 до число_записей - 1:
        запись ← прочитать следующую запись из файла
        если запись.номер = ключ:
            вернуть запись
    вернуть НЕ_НАЙДЕНО
```

Лучший случай — одна проверка (ключ в первой записи); худший случай — `n` чтений (ключ в последней записи или отсутствует). При равномерном расположении найденного ключа среднее число просмотренных записей приблизительно равно `n/2`. Временная сложность поиска — `O(n)`, дополнительная память — `O(1)`.

### 3.2 Функция поиска и контракт

Предусловия: бинарный файл открыт, его размер кратен размеру записи, все записи имеют одинаковый формат; строка `key` является искомым номером. Постусловия: функция возвращает запись с этим номером, если она присутствует, иначе — `std::nullopt`; содержимое файла не меняется. Сложность — не более `n` последовательных чтений.

**Листинг 1 — Функция последовательного поиска в бинарном файле (`common/src/RecordFile.cpp`).**

```cpp
std::optional<CarRecord> BinaryRecordFile::linearSearch(const std::string& key) {
    stream_.clear();
    stream_.seekg(0, std::ios::beg);
    if (!stream_) {
        throw std::runtime_error("Не удалось установить начало бинарного файла");
    }

    for (std::size_t i = 0; i < recordCount_; ++i) {
        CarRecord record{};
        stream_.read(reinterpret_cast<char*>(&record),
                     static_cast<std::streamsize>(sizeof(CarRecord)));
        if (stream_.gcount() != static_cast<std::streamsize>(sizeof(CarRecord))) {
            throw std::runtime_error("Ошибка чтения записи " + std::to_string(i));
        }
        if (getCarNumber(record) == key) {
            return record;
        }
    }
    return std::nullopt;
}
```

Функция вызывается терминальным приложением `task_2_app`. При запуске с `--search НОМЕР` программа открывает `data/records.bin`, выполняет поиск и выводит поля найденной записи. В интерактивном режиме номер запрашивается через стандартный ввод. Если демонстрационного файла ещё нет, программа автоматически создаёт текстовый и бинарный файлы со 100 записями.

## 4. Задание 3. Поиск Фибоначчи с дополнительным индексом

### 4.1 Постановка задачи и таблица ссылок

Для ускорения поиска требуется сформировать в оперативной памяти таблицу, содержащую поисковый ключ и ссылку на соответствующую запись бинарного файла. После построения таблица сортируется по номеру автомобиля. Поиск Фибоначчи применяется к отсортированному индексу; найденное смещение используется для чтения исходной записи из файла.

**Таблица 5 — Состав элемента дополнительного индекса и назначение его полей.**

| Поле индекса | Тип C++ | Назначение |
|---|---|---|
| `key` | `std::string` | Номер автомобиля, по которому выполняется поиск |
| `byteOffset` | `std::uint64_t` | Смещение начала исходной записи в бинарном файле, `i × 153` |

В программе таблица реализована как `std::vector<KeyOffset>`. Ссылка хранит **байтовое смещение**, а не указатель на адрес оперативной памяти: поэтому запись можно прочитать даже после того, как позиция потока изменилась. Для перехода применяются стандартные средства C++ `std::ifstream::seekg` и `std::ifstream::read`. Индекс строится один раз: файл последовательно читается, пары «номер — смещение» добавляются в вектор, затем `std::sort` упорядочивает пары по ключу. Исходный файл при этом остаётся в произвольном порядке.

### 4.2 Алгоритм Фибоначчи

Поиск Фибоначчи требует упорядоченного массива. Он поддерживает три соседних числа Фибоначчи, размер текущего окна и смещение последней исключённой позиции. В зависимости от сравнения с ключом-кандидатом алгоритм отбрасывает левую или правую часть массива.

Псевдокод поиска в индексе:

```text
ПОИСК_ФИБОНАЧЧИ(индекс, ключ):
    n ← длина индекса
    если n = 0: вернуть НЕ_НАЙДЕНО
    найти минимальное Fm, для которого Fm ≥ n
    offset ← -1
    пока Fm > 1:
        i ← min(offset + F(m-2), n - 1)
        если индекс[i].ключ < ключ:
            отбросить левую часть; сдвинуть числа Фибоначчи вправо
            offset ← i
        иначе если индекс[i].ключ > ключ:
            уменьшить окно слева; сдвинуть числа Фибоначчи
        иначе:
            вернуть i
    проверить оставшийся элемент offset + 1
    вернуть НЕ_НАЙДЕНО
```

Вспомогательная функция поиска возвращает позицию в индексе, а `fibonacciSearchOffset` преобразует её в байтовую ссылку на исходную запись. Время поиска ключа в индексе — `O(log n)` сравнений, чтение целевой записи выполняется одним прямым доступом к файлу. Построение индекса требует `O(n log n)` времени из-за сортировки и `O(n)` дополнительной памяти.

### 4.3 Функция поиска и контракт

Предусловия функции `fibonacciSearchPosition`: индекс отсортирован по возрастанию ключа, ключи уникальны. Постусловие: возвращается позиция `p`, для которой `index[p].key == key`, либо `std::nullopt`, если совпадения нет. Функция `fibonacciSearchOffset` получает ключ и отсортированный индекс и возвращает именно требуемую заданием ссылку — байтовое смещение записи; при отсутствии ключа возвращает `std::nullopt`. Функция `fibonacciSearchRecord` принимает найденное смещение, выполняет прямое чтение файла и возвращает запись. Предусловие чтения: бинарный файл соответствует построенному индексу, смещение кратно 153 и указывает внутрь файла; постусловие — верная запись либо отсутствие результата.

**Листинг 2 — Основной цикл поиска Фибоначчи в упорядоченном индексе (`common/src/Search.cpp`).**

```cpp
std::optional<std::size_t> fibonacciSearchPosition(
    const std::vector<KeyOffset>& sortedIndex,
    const std::string& key) {
    const std::size_t n = sortedIndex.size();
    if (n == 0) {
        return std::nullopt;
    }

    std::size_t fibMm2 = 0; // F(m - 2)
    std::size_t fibMm1 = 1; // F(m - 1)
    std::size_t fibM = fibMm2 + fibMm1;
    while (fibM < n) {
        fibMm2 = fibMm1;
        fibMm1 = fibM;
        fibM = fibMm2 + fibMm1;
    }

    std::ptrdiff_t offset = -1;
    while (fibM > 1) {
        const auto candidateSigned = offset + static_cast<std::ptrdiff_t>(fibMm2);
        const std::size_t candidate = std::min(
            static_cast<std::size_t>(candidateSigned), n - 1);
        const std::string& candidateKey = sortedIndex[candidate].key;

        if (candidateKey < key) {
            fibM = fibMm1;
            fibMm1 = fibMm2;
            fibMm2 = fibM - fibMm1;
            offset = static_cast<std::ptrdiff_t>(candidate);
        } else if (candidateKey > key) {
            fibM = fibMm2;
            fibMm1 = fibMm1 - fibMm2;
            fibMm2 = fibM - fibMm1;
        } else {
            return candidate;
        }
    }

    const auto finalPosition = offset + 1;
    if (fibMm1 != 0 && finalPosition >= 0 &&
        static_cast<std::size_t>(finalPosition) < n &&
        sortedIndex[static_cast<std::size_t>(finalPosition)].key == key) {
        return static_cast<std::size_t>(finalPosition);
    }
    return std::nullopt;
}
```

Функция поиска ссылки возвращает байтовое смещение, а отдельная функция выполняет чтение по этой ссылке:

```cpp
std::optional<std::uint64_t> fibonacciSearchOffset(
    const std::vector<KeyOffset>& sortedIndex,
    const std::string& key) {
    const auto position = fibonacciSearchPosition(sortedIndex, key);
    if (!position) {
        return std::nullopt;
    }
    return sortedIndex[*position].byteOffset;
}

std::optional<CarRecord> fibonacciSearchRecord(
    BinaryRecordFile& file,
    const std::vector<KeyOffset>& sortedIndex,
    const std::string& key) {
    const auto byteOffset = fibonacciSearchOffset(sortedIndex, key);
    if (!byteOffset) {
        return std::nullopt;
    }
    return file.readAtOffset(*byteOffset);
}
```

### 4.4 Тестирование для 100 записей

## 5. Анализ эффективности

### 5.1 Методика измерений

Приложения для линейного поиска и поиска Фибоначчи создают файлы для 100, 1 000 и 10 000 записей. Для каждого размера используются одни и те же генератор записей и фиксированный seed; ключи в запросах случайно выбираются из существующих номеров. Поэтому доля успешных запросов в измерении равна 100 %. Выполняются 10 прогревочных запросов, не включаемых в результат, затем 5 серий по 100 запросов — всего 500 запросов для каждой строки таблицы. Используется `std::chrono::steady_clock`; результат указан как среднее время одного поиска в микросекундах.

В замер включена работа алгоритма и необходимое чтение бинарного файла: линейный алгоритм последовательно читает записи, алгоритм Фибоначчи после нахождения ссылки делает `seekg`/`read` целевой записи. Открытие файла и генерация данных не входят в замер. Для задания 3 построение и сортировка индекса также выполняются **до** начала замера. Такое сравнение характеризует повторный поиск по уже подготовленному индексу; если выполняется единственный запрос, стоимость построения индекса следует учитывать отдельно.

Измерение выполнено в Linux x86-64, Intel Xeon Processor @ 2.60 GHz, GCC 12.2.0, C++17, конфигурация CMake `Release`. Время зависит от процессора, компилятора, файловой системы и кэширования файлов ОС; поэтому результаты других запусков могут отличаться.

**Таблица 10 — Теоретические характеристики реализованных вариантов поиска.**

| Алгоритм | Предварительная подготовка | Поиск одного ключа | Дополнительная память |
|---|---|---|---|
| Линейный поиск в файле | Не требуется | `O(n)` чтений/сравнений; лучший случай `O(1)` | `O(1)` |
| Поиск Фибоначчи по индексу | Считать файл и отсортировать индекс: `O(n log n)` | `O(log n)` сравнений в памяти и одно чтение записи по смещению | `O(n)` пар «ключ — смещение» |

Эксперимент показывает, что повторный поиск по готовому индексу быстрее линейного просмотра, особенно для большего файла. При этом нельзя сравнивать только время одного поиска без учёта подготовки: для нескольких запросов сортировка индекса амортизируется, а для единичного запроса стоимость построения может быть существенной. Линейный алгоритм проще и не требует памяти под индекс, поэтому остаётся подходящим для небольших файлов или редких запросов.

## 6. Заключение

В ходе работы реализованы три терминальных приложения на C++17. Первое формирует уникальные записи автомобилей в текстовом файле и затем преобразует их в бинарный файл фиксированного формата. Второе выполняет линейный поиск номера в бинарном файле. Третье строит в оперативной памяти индекс из номера и байтового смещения, ищет ключ алгоритмом Фибоначчи и читает исходную запись прямым доступом.

Для набора из 100 записей проверены генерация, преобразование, уникальность номеров, чтение по смещению, успешный и неуспешный поиск. Автоматические тесты пройдены. На текущей тестовой среде среднее время линейного поиска выросло с 2,598 мкс при 100 записях до 237,755 мкс при 10 000 записях. Поиск Фибоначчи с заранее построенным индексом и чтением записи занял от 0,735 до 1,528 мкс. Максимальное измеренное ускорение для 10 000 записей составило примерно 155,6 раза. Полученные результаты подтверждают преимущество индексирования при повторных запросах и одновременно показывают, что стоимость построения индекса необходимо учитывать для конкретного сценария использования.
