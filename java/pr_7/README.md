# Практическая работа №7 — Java

**Тема:** Паттерны проектирования: структурные и поведенческие паттерны (Вариант №4 — Decorator и Mediator).

Простая реализация обоих заданий 4-го варианта практической работы №7 (структурный паттерн `Decorator` — форматирование текста; поведенческий паттерн `Mediator` — система чата) и готовый отчёт по ГОСТ [`report.md`](./report.md).

---

## Что делал?

1. **Структурный паттерн — Вариант №4 (`Decorator`, Декоратор)** — сделал систему форматирования текста: интерфейс `Text` с методом `display()`, базовый класс `PlainText`, абстрактный декоратор `TextDecorator` и три конкретных декоратора — `BoldTextDecorator` (жирный), `ItalicTextDecorator` (курсив) и `UnderlineTextDecorator` (подчёркнутый). В `DecoratorDemo` показал, что их можно вкладывать друг в друга в любом порядке.
2. **Поведенческий паттерн — Вариант №4 (`Mediator`, Посредник)** — реализовал систему чата: интерфейс посредника `Mediator`, комнату чата `ChatRoom` и класс пользователя `User`. Пользователи не хранят ссылки друг на друга, а отправляют и получают сообщения только через общего посредника `ChatRoom`.

## Как работают ключевые методы?

### Часть 1 — Decorator (`decorator`)

- **`PlainText.display()`** — просто выводит исходную строку без тегов.
- **`TextDecorator`** — одновременно реализует `Text` и хранит внутри поле `protected final Text decoratedText`. В своём `display()` делегирует вызов вложенному объекту: `decoratedText.display()`.
- **`BoldTextDecorator.display()`, `ItalicTextDecorator.display()`, `UnderlineTextDecorator.display()`** — печатают открывающий тег (`<b>`, `<i>` или `<u>`), вызывают `super.display()`, а затем печатают закрывающий тег (`</b>`, `</i>` или `</u>`). Так как каждый декоратор принимает в конструктор любой объект типа `Text` (как `PlainText`, так и другой декоратор), их можно комбинировать в произвольном порядке без изменения существующих классов.

### Часть 2 — Mediator (`mediator`)

- **`ChatRoom.addUser(User user)`** — регистрирует нового участника в списке `users` (с защитой от `null` и повторного добавления).
- **`User.send(String message)`** — выводит, кто отправил сообщение, и передаёт его посреднику вызовом `mediator.sendMessage(message, this)`.
- **`ChatRoom.sendMessage(String message, User sender)`** — пробегает по списку всех участников чата и для каждого, кроме самого отправителя (`user != sender`), вызывает `user.receive(message, sender.getName())`.
- **`User.receive(String message, String senderName)`** — отображает входящее сообщение у получателя.

## Как это связано?

```text
Часть 1 — Decorator (пакет decorator):
  Text <|.. PlainText
  Text <|.. abstract TextDecorator ◇── (оборачивает Text)
                 ├── BoldTextDecorator
                 ├── ItalicTextDecorator
                 └── UnderlineTextDecorator
  DecoratorDemo ──> собирает матрёшку декораторов в любом порядке

Часть 2 — Mediator (пакет mediator):
  Mediator <|.. ChatRoom ──(хранит List<User>)──> User
                    ^                              │
                    └──── sendMessage(msg, this) ──┘
  MediatorDemo ──> создаёт ChatRoom, регистрирует пользователей и запускает переписку
```

В `Decorator` объекты складываются цепочкой «матрёшкой» вокруг `PlainText`, динамически наращивая форматирование. В `Mediator` все связи собираются «звездой» вокруг `ChatRoom`, благодаря чему пользователи полностью отвязаны друг от друга.

## Контрольные вопросы (для защиты)

1. **В чём разница между структурными и поведенческими паттернами?**  
   Структурные паттерны (как `Decorator`) отвечают за то, как классы и объекты объединяются в более крупные гибкие структуры. Поведенческие паттерны (как `Mediator`) отвечают за взаимодействие между объектами и распределение обязанностей.

2. **Почему в задаче форматирования текста Decorator удобнее обычного наследования?**  
   При обычном наследовании пришлось бы создавать отдельный класс на каждую комбинацию стилей (`BoldItalicText`, `BoldUnderlineText`, `BoldItalicUnderlineText` и т. д.). С декоратором достаточно трёх маленьких классов, которые комбинируются на лету в любом порядке.

3. **Почему декораторы можно применять в любом порядке?**  
   Потому что и базовый `PlainText`, и каждый декоратор реализуют один и тот же интерфейс `Text`, а конструктор любого декоратора принимает параметр типа `Text`.

4. **Какую главную выгоду даёт паттерн Mediator в системе чата?**  
   Он снижает связанность (coupling): вместо связей «каждый с каждым» между $N$ пользователями каждый объект `User` знает только об интерфейсе `Mediator`. Добавить нового пользователя или поменять правила рассылки можно в `ChatRoom`, не трогая класс `User`.

5. **Почему в `ChatRoom.sendMessage()` стоит проверка `user != sender`?**  
   Чтобы пользователь не получал обратно собственное же сообщение, которое он только что отправил в общий чат.
