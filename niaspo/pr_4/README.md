# Как это работает: два контейнера, общающиеся через localhost

Практическая работа №4, часть 1 «Межконтейнерное взаимодействие docker-контейнеров
через localhost». Проект: `docker_pr4/`. Отчёт по работе — `report.md`, здесь — подробный
разбор «с нуля»: что собрано, как запускать, что должно получиться и что делать, если
не получилось.

Если ты ничего не знаешь про Docker — начни с раздела 1: там объясняется, что такое
контейнер, порт и почему `localhost` внутри контейнера не то же самое, что `localhost`
на твоей машине. Дальше — по шагам.

---

# 1. Базовые понятия (совсем коротко)

**Контейнер** — это программа, упакованная вместе с библиотеками и настройками в один
образ, который можно одинаково запустить на любой машине с Docker. Запущенный образ —
это контейнер. У него своя файловая система, свой список процессов и **свой сетевой
стек**.

**Порт** — числовой адрес внутри сетевого стека. «Программа слушает порт 8082» значит,
что она принимает TCP-соединения, адресованные на порт 8082 этой машины. Две программы
могут жить на одном адресе, только если у них разные порты, — поэтому в этой работе
один обработчик на `localhost:8081`, а другой на `localhost:8082`.

**`localhost` (127.0.0.1)** — это адрес текущего сетевого стека, то есть «я сам».

> **Главная мысль всей работы.** У каждого обычного контейнера свой сетевой стек, и
> `localhost` внутри контейнера — это сам контейнер. Обращение к `localhost:8082` из
> контейнера №1 в обычном режиме придёт **в контейнер №1**, а не к соседу (и, скорее
> всего, будет `Connection refused`). Именно поэтому задание «заставить контейнеры
> общаться через `localhost`» требует поменять режим сети.

**`network_mode: host`** — режим, в котором контейнер не получает собственный сетевой
стек, а использует сетевое пространство имён хоста. Тогда `localhost` внутри контейнера
— это буквально `localhost` твоей машины, а порт, который слушает программа в
контейнере, занят на хосте. Так два контейнера на хосте видят друг друга по
`localhost` и различаются только портами: 8081 и 8082. Это ровно то, что требует
задание.

Плата за это: у контейнеров нет сетевой изоляции. Приложения, слушающие порты, висят
прямо на хосте, и порт нельзя переехать «внутрь» контейнера через `-p`. В работе это
осознанный выбор — он нужен для выполнения задания. Альтернатива описана в разделе 7.

# 2. Что именно собрано

Два контейнера и одна программа-посредник в терминале:

```
                       хостовый стек сети (network_mode: host)
   ┌───────────────────────────────────────────────────────────────────────┐
   │                                                                       │
   │  пользователь                                                         │
   │  (браузер или curl)                                                   │
   │       │  ① GET / , POST /api/process                                  │
   │       ▼                                                               │
   │  ┌─────────────────────────────┐                                      │
   │  │ контейнер №1 «шлюз»         │  ② POST /process                     │
   │  │ Flask + gunicorn            │ ───────────────────────────┐         │
   │  │ localhost:8081              │                            ▼         │
   │  │                             │        ┌───────────────────────────┐ │
   │  │                             │        │ контейнер №2 «обработчик» │ │
   │  │                             │  ③     │ Flask + gunicorn          │ │
   │  │                             │ ◄──────│ localhost:8082            │ │
   │  └─────────────────────────────┘  JSON  └───────────────────────────┘ │
   │       │  ④ итоговый JSON                                              │
   │       ▼                                                               │
   └───────────────────────────────────────────────────────────────────────┘
```

| Сервис compose | Контейнер | Слушает | Роль | Кто вызывает |
|---|---|---|---|---|
| `gateway` | `pr4_gateway` | `localhost:8081` | принимает запрос пользователя, вызывает №2, склеивает ответ | пользователь |
| `compute` | `pr4_compute` | `localhost:8082` | обрабатывает текст, возвращает результат | только контейнер №1 |

Структура файлов:

```
docker_pr4/
├── docker-compose.yml        # описание двух сервисов: образы, порты, режим сети
├── .env                      # номера портов (GATEWAY_PORT, COMPUTE_PORT)
├── verify.sh                 # автопроверка всей цепочки, печатает ✓/✗
├── gateway/                  # контейнер №1
│   ├── Dockerfile            # как собрать образ шлюза
│   ├── requirements.txt      # Flask, gunicorn, requests
│   ├── app.py                # код шлюза
│   └── templates/index.html  # страница для пользователя
└── compute/                  # контейнер №2
    ├── Dockerfile
    ├── requirements.txt      # Flask, gunicorn (requests не нужен: он никого не вызывает)
    └── app.py                # код обработчика
```

# 3. Как устроен каждый контейнер

## 3.1. Контейнер №2 «обработчик» (`compute/`)

Самый простой: он ничего не знает про контейнер №1 и не делает исходящих запросов. Его
задача — принять текст, посчитать по нему статистику, отдать JSON.

| Метод и путь | Что делает |
|---|---|
| `GET /` | справка о сервисе: имя, имя хоста, порт, список эндпоинтов |
| `GET /health` | `{"status":"ok"}` — по нему Docker понимает, что контейнер жив |
| `POST /process` | принимает JSON `{"text": "..."}`, возвращает статистику и SHA-256 |

Что возвращает `POST /process`:

```json
{
  "request_id": "040656643c7f",
  "service": "Контейнер №2",
  "processed_at": "2026-11-10T12:17:49Z",
  "result": {
    "chars": 52,
    "chars_no_spaces": 46,
    "words": 7,
    "unique_words": 7,
    "longest_word": "Контейнеры",
    "sha256": "77cbc8ced99f563512d822e60b060bcc0d55f08d561d7358e0e5d03de64bbc01"
  },
  "processing_ms": 0.187
}
```

`request_id` приходит в заголовке `X-Request-Id` от шлюза и возвращается обратно — по
нему в журналах обоих контейнеров видно один и тот же запрос. Это простейшая
«трассировка»: без неё в логах два запроса не отличить друг от друга.

Проверки входа (`400` в ответ): поле `text` отсутствует, пустое или не строка; текст
длиннее 10000 символов. Это граница между двумя сервисами — мусор сюда попадать не
должен.

## 3.2. Контейнер №1 «шлюз» (`gateway/`)

Он делает две вещи: общается с пользователем и вызывает контейнер №2.

| Метод и путь | Что делает |
|---|---|
| `GET /` | HTML-страница: поле ввода, кнопка, вывод JSON |
| `GET /health` | собственная живость |
| `GET /chain` | «а №2 доступен?» — `200`, если да, `503`, если нет |
| `POST /api/process` | главная логика: пользователь → №2 → ответ пользователю |

Как выглядит вызов соседа (`gateway/app.py`):

```python
NEXT_URL = os.environ.get("NEXT_URL", "http://localhost:8082")

response = requests.post(
    f"{NEXT_URL}/process",
    json={"text": text},
    headers={"X-Request-Id": request_id},
    timeout=UPSTREAM_TIMEOUT,          # 5 с по умолчанию
)
```

Три важные детали:

1. **Адрес берётся из переменной окружения**, а не «зашит» в код. В `docker-compose.yml`
   стоит `NEXT_URL: "http://localhost:8082"`. Захотел другой порт — поменял переменную.
2. **`timeout` обязателен.** Без него, если сосед завис, шлюз будет ждать бесконечно и
   накопит висящие соединения.
3. **Ошибки соседа не роняют шлюз.** `requests.RequestException` перехватывается, и
   пользователь получает `502` с текстом причины. Шлюз остаётся живым — это важно:
   иначе один упавший сервис утащил бы за собой всю цепочку.

Форма ответа пользователю собирается из двух частей — видно, кто что добавил:

```json
{
  "request_id": "040656643c7f",                        ← шлюз
  "gateway": {"service": "Контейнер №1", ...},          ← шлюз
  "upstream": {"url": "http://localhost:8082/process",  ← шлюз: как прошёл вызов
               "ok": true, "status": 200, "elapsed_ms": 3.729},
  "answer": {"service": "Контейнер №2", "result": {...}},  ← ответ контейнера №2 целиком
  "total_ms": 3.912                                     ← полное время, включая оба хопа
}
```

## 3.3. Dockerfile: почему именно так

Оба Dockerfile почти одинаковы; разберём на примере шлюза:

```dockerfile
FROM python:3.12-slim                 # базовый образ: Python 3.12 без лишнего

ENV PORT=8081 \                       # номер порта — переменной, а не константой в коде
    NEXT_URL=http://localhost:8082 \   # адрес соседа
    SERVICE_NAME="Контейнер №1"

WORKDIR /app                          # рабочая директория внутри образа
COPY requirements.txt ./              # сначала только список зависимостей
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py ./                        # потом код
COPY templates/ ./templates/

RUN useradd --create-home --uid 10001 appuser && chown -R appuser:appuser /app
USER appuser                          # процесс работает не от root

EXPOSE 8081                           # документация: «сервис слушает 8081»
HEALTHCHECK ... CMD python -c "...urlopen('http://127.0.0.1:8081/chain'...)"
CMD ["sh", "-c", "exec gunicorn --bind 0.0.0.0:${PORT} --workers 1 --access-logfile - app:app"]
```

Что здесь стоит понимать:

- **Порядок `COPY requirements.txt` → `pip install` → `COPY app.py`.** Docker кэширует
  каждый слой. Пока не менялся `requirements.txt`, `pip install` берётся из кэша, и
  правка `app.py` пересобирается за секунды, а не за минуту.
- **`USER appuser`.** Приложение не работает от root. Если в коде найдётся уязвимость,
  ущерб ограничен правами обычного пользователя.
- **`--bind 0.0.0.0`.** Слушать на всех интерфейсах, а не только на `127.0.0.1`. В
  режиме `network_mode: host` это означает «порт хоста на всех интерфейсах». Важная
  деталь: `EXPOSE` сам по себе порт никуда не открывает, это только описание.
- **`--access-logfile -`.** Журнал доступа gunicorn пишет в stdout, поэтому он виден в
  `docker compose logs`. Без этого там была бы тишина.
- **`HEALTHCHECK`.** Docker периодически сам дергает `/health` (`/chain` у шлюза). Если
  проверка не проходит, контейнер получает статус `unhealthy`. По этому статусу
  `depends_on: condition: service_healthy` задерживает старт шлюза, пока обработчик не
  поднялся.

## 3.4. `docker-compose.yml` построчно

```yaml
name: docker_pr4                    # имя проекта: контейнеры/сети получают этот префикс

services:                           # список контейнеров
  gateway:
    build:                          # собрать образ из своего Dockerfile
      context: ./gateway            #   из каталога gateway/
      dockerfile: Dockerfile
    image: pr4/gateway:1.0          # как назвать собранный образ
    container_name: pr4_gateway     # фиксированное имя контейнера (иначе docker_pr4-gateway-1)
    environment:                    # переменные окружения внутрь контейнера
      PORT: "8081"
      NEXT_URL: "http://localhost:8082"
    network_mode: host              # ← ключевая строка: общий сетевой стек с хостом
    depends_on:
      compute:
        condition: service_healthy  # стартовать, только когда №2 пройдёт healthcheck
    restart: unless-stopped         # перезапускать при падении, но не после ручного stop

  compute:
    build:
      context: ./compute
    image: pr4/compute:1.0
    container_name: pr4_compute
    environment:
      PORT: "8082"
    network_mode: host
    restart: unless-stopped
```

Секции `ports:` здесь нет вовсе — и это правильно. `ports` нужен, чтобы «выставить»
порт контейнера на хост, когда у контейнера **свой** сетевой стек. В режиме `host`
никакого разделения нет: порт, который слушает программа в контейнере, уже является
портом хоста. Если добавить `ports` в `network_mode: host`, Docker выдаст
предупреждение и проигнорирует секцию.

# 4. Подготовка и запуск

## 4.1. Что должно быть установлено

Arch Linux (как в предыдущих работах):

```bash
sudo pacman -Syu docker docker-compose docker-buildx
sudo systemctl enable --now docker
sudo usermod -aG docker "$USER"   # чтобы работать без sudo (нужен перелогин)
```

Проверка:

```bash
docker --version            # Docker version 29.7.2
docker compose version      # Docker Compose version v2.x
docker run --rm hello-world # «Hello from Docker!»
```

## 4.2. Свободны ли порты 8081 и 8082

В режиме `host` порты занимаются на самой машине, поэтому их может занять кто-то
другой:

```bash
ss -tulpn | grep -E '8081|8082'
```

Пусто — всё хорошо. Если занято, вариантов два: освободить порт или поменять номера
(см. раздел 6.2, «Поменять порты»).

## 4.3. Сборка и запуск

```bash
cd pr_4/docker_pr4
docker compose up -d --build
```

`--build` — пересобрать образы (первый раз обязательно), `-d` — в фоне.

Первая сборка скачивает `python:3.12-slim` (~50 МБ) и ставит Flask с gunicorn: 1–3
минуты в зависимости от сети. Повторная — секунды.

Проверить, что поднялось:

```bash
docker compose ps
```

```
NAME           IMAGE             SERVICE   STATUS                   PORTS
pr4_compute    pr4/compute:1.0   compute   Up 12 seconds (healthy)
pr4_gateway    pr4/gateway:1.0   gateway   Up 5 seconds (healthy)
```

Колонка `PORTS` пустая — так и должно быть в режиме `host` (см. раздел 3.4).
`(healthy)` появляется через несколько секунд после старта: это отработал HEALTHCHECK.

## 4.4. Открыть страницу

Браузер: **<http://localhost:8081>**

Что увидишь: тёмную страницу «Межконтейнерное взаимодействие через localhost», схему
цепочки, поле с готовым текстом и кнопки. Нажми «Отправить запрос» — в блоке «Ответ»
появится JSON с результатом обработки и временем (обычно 2–10 мс). Кнопка «Проверить
связь с №2» вызывает `/chain` и показывает, доступен ли обработчик.

## 4.5. Проверки из терминала (то же самое, без браузера)

```bash
# 1. обработчик жив
curl -s http://localhost:8082/health
# → {"status":"ok","service":"Контейнер №2","uptime_sec":61.9}

# 2. шлюз жив
curl -s http://localhost:8081/health
# → {"status":"ok","service":"Контейнер №1","uptime_sec":137.5}

# 3. видит ли шлюз обработчик
curl -s http://localhost:8081/chain
# → {"service":"Контейнер №1","upstream":{"ok":true,"body":{...}}}

# 4. полная цепочка
curl -s -X POST http://localhost:8081/api/process \
     -H "Content-Type: application/json" \
     -d '{"text":"Контейнеры общаются через localhost на разных портах"}'
# → JSON с блоками gateway / upstream / answer / total_ms

# 5. то же самое формой, как это делает страница
curl -s -X POST http://localhost:8081/api/process -d 'text=короткий текст'
```

## 4.6. Автопроверка

```bash
chmod +x verify.sh     # если бит выполнения не сохранился
./verify.sh
```

Скрипт идёт по шагам: окружение → контейнеры → порт 8082 → порт 8081 → связь №1 → №2
→ полная цепочка → страница. В конце — `ИТОГ: все проверки пройдены (9)`. Удобно, чтобы
показать работу преподавателю, не набирая восемь команд вручную.

> В `verify.sh` экспортируется `no_proxy="localhost,127.0.0.1,::1"` и в `curl` стоит
> `--noproxy '*'`. Это не украшение: если в системе настроен HTTP-прокси (VPN-клиент,
> корпоративная сеть), `curl` может отправить запрос к `localhost` **в прокси** и
> получить `Recv failure: Connection reset by peer`. Обход прокси убирает эту
> неочевидную проблему.

## 4.7. Логи

```bash
docker compose logs -f            # оба контейнера
docker compose logs -f gateway    # только шлюз
docker compose logs -f --tail=20 compute
```

Ожидаемая картина после одного запроса: в журнале шлюза — `GET /` от браузера и
`POST /api/process`; в журнале обработчика — `POST /process`, причём клиент
`python-requests/2.34.2`, то есть запрос сделал контейнер №1, а не пользователь.

```
pr4_gateway  | 127.0.0.1 - - [10/Nov/2026:12:17:49] "POST /api/process HTTP/1.1" 200 737 "-" "curl/7.88.1"
pr4_compute  | 127.0.0.1 - - [10/Nov/2026:12:17:49] "POST /process HTTP/1.1" 200 456 "-" "python-requests/2.34.2"
```

Время у обеих строк одинаковое, `request_id` в JSON — тоже: это один и тот же запрос,
прошедший два хопа.

# 5. Чему учит эта работа (сводка механизмов)

1. **`localhost` — относительное понятие.** В обычном контейнере это сам контейнер; в
   режиме `host` — машина-хост. От режима сети зависит, куда реально уйдёт запрос.
2. **`network_mode: host`** даёт общий `localhost` для нескольких контейнеров. Различие
   между сервисами — только порты. Это буквальное решение задания.
3. **Один порт — один слушатель.** Два контейнера на одном порту не уживутся: второй
   упадёт с `Address already in use`. Поэтому 8081 и 8082, а не 8081 и 8081.
4. **`depends_on` + `healthcheck`** задают порядок запуска: шлюз не начнёт работу, пока
   обработчик не ответит на `/health`. Просто `depends_on: [compute]` ждал бы только
   факта старта контейнера, а не готовности приложения.
5. **HTTP-вызов между сервисами** — это обычный клиент (`requests`) + `timeout` +
   обработка исключений. Таймаут и перехват ошибок обязательны, иначе один медленный
   сосед останавливает всю цепочку.
6. **Ошибки передаются осмысленно.** Шлюз отвечает `502`, когда сосед не ответил, и
   `503` на `/chain`; в теле — причина (`Connection refused`). Отладка сводится к
   чтению одного JSON вместо гадания.
7. **Переменные окружения вместо констант.** Порт и адрес соседа задаются в
   `docker-compose.yml`, код править не нужно.

# 6. Типовые задачи и изменения

## 6.1. Остановить и запустить

```bash
docker compose stop compute        # остановить только обработчик
docker compose start compute       # вернуть его
docker compose restart gateway     # перезапустить шлюз
docker compose stop                # остановить всё
docker compose down                # удалить контейнеры и образы проекта (данных тут нет)
docker compose up -d               # снова поднять без пересборки
```

## 6.2. Поменять порты

Порты вынесены в `.env` рядом с `docker-compose.yml`:

```bash
# .env
GATEWAY_PORT=8081
COMPUTE_PORT=8082
```

Compose сам подхватывает этот файл и подставляет значения в `${GATEWAY_PORT}` и
`${COMPUTE_PORT}` (а `:-8081` — значение по умолчанию, если переменной нет). Хочешь
9081/9082 — правь `.env`:

```bash
GATEWAY_PORT=9081
COMPUTE_PORT=9082
```

```bash
docker compose up -d      # пересоздаст контейнеры с новыми переменными
```

Пересборка образов не нужна: оба приложения читают порт из переменной `PORT`, а
`NEXT_URL` шлюза собирается из `${COMPUTE_PORT}`, поэтому адрес соседа меняется
согласованно. Сначала проверь, что новые порты свободны: `ss -tulpn | grep -E '9081|9082'`.

## 6.3. Поменять обработку в контейнере №2

Правь `compute/app.py`. Помни: код **копируется в образ** при сборке, поэтому просто
сохранить файл недостаточно.

```bash
docker compose up -d --build compute
```

То же для шлюза: `docker compose up -d --build gateway`. Если правил оба — `docker
compose up -d --build` без имени сервиса.

## 6.4. Обратиться к обработчику напрямую

Это возможно и полезно для отладки — обработчик торчит на `localhost:8082`:

```bash
curl -s -X POST http://localhost:8082/process \
     -H "Content-Type: application/json" \
     -d '{"text":"проверка напрямую"}'
```

Если так работает, а через шлюз — нет, проблема в связке №1 → №2, а не в самом №2.

# 7. Альтернатива: bridge-сеть вместо `host`

В режиме `host` сетевая изоляция контейнеров пропадает: приложения слушают порты
машины. Если изоляция нужна, а общение «через localhost» не является жёстким условием,
делают так: создают пользовательскую сеть, и контейнеры обращаются друг к другу по
**имени сервиса**, а не по `localhost`.

```yaml
services:
  gateway:
    environment:
      NEXT_URL: "http://compute:8082"   # имя сервиса вместо localhost
    ports:
      - "8081:8081"                     # наружу выставлен только шлюз
    networks: [pr4_net]
  compute:
    networks: [pr4_net]                 # наружу не выставлен вовсе

networks:
  pr4_net:
    driver: bridge
```

Внутри такой сети работает DNS Docker: имя `compute` резолвится в IP контейнера. Плюсы:
порты обработчика недоступны снаружи, контейнеры изолированы от хоста. Минус
применительно к этой работе: обращение идёт не через `localhost`, а по имени — то есть
задание «через localhost» выполнено не буквально.

Историческая альтернатива — опция `--link` (`docker run --link compute:compute`). Она
устарела: работает только в одну сторону, не даёт изоляции и не поддерживается в
compose v2 для новых проектов. Именно поэтому в задании она упомянута как материал для
ознакомления, а не как рекомендуемое решение.

# 8. Если что-то пошло не так

| Симптом | Причина | Что делать |
|---|---|---|
| `Bind for 0.0.0.0:8081 failed: port is already allocated` / `Address already in use` в логах, контейнер циклически перезапускается | порт занят на хосте (в режиме `host` порты общие с машиной) | `ss -tulpn \| grep -E '8081\|8082'`, освободить порт или сменить номер (6.2) |
| `permission denied while trying to connect to the Docker daemon socket` | нет прав на `/var/run/docker.sock` | `sudo usermod -aG docker $USER` + перелогин, либо запускать через `sudo` |
| `Cannot connect to the Docker daemon` | демон не запущен | `sudo systemctl start docker` |
| `docker: 'compose' is not a docker command` | не установлен плагин compose | `sudo pacman -S docker-compose` |
| браузер: «сайт недоступен» на `http://localhost:8081`, а `curl` из терминала отвечает `200` | прокси в браузере или VPN-клиент перехватывает `localhost` | отключить прокси для localhost либо открыть `http://127.0.0.1:8081` |
| `curl: (56) Recv failure: Connection reset by peer` | то же, но для `curl`: запрос ушёл в `http_proxy` из окружения | `curl --noproxy '*' http://localhost:8081/...`; проверить `env \| grep -i proxy` |
| `502` на `POST /api/process`, в теле `Connection refused` | контейнер №2 не запущен или слушает другой порт | `docker compose ps`, `docker compose logs compute`; сверить `PORT` у №2 и `NEXT_URL` у №1 |
| `503` на `GET /chain` | то же: №1 не видит №2 | как выше |
| `400` «поле 'text' обязательно» | пустой `text` или запрос без `Content-Type: application/json` | передать `-H "Content-Type: application/json"` и непустой текст |
| контейнер в статусе `unhealthy` | не проходит HEALTHCHECK: приложение не слушает порт или упало | `docker compose logs <сервис> --tail=50` |
| `docker compose up` падает на `pip install` | нет сети/мешает прокси | повторить сборку: `docker compose build --no-cache gateway` |
| правки в `app.py` «не применяются» | код не попал в образ | `docker compose up -d --build <сервис>` |
| `no space left on device` | старые образы | `docker system df`, затем `docker system prune -a` |

# 9. Шпаргалка

```bash
# состояние и логи
docker compose ps                       # контейнеры проекта
docker compose logs -f gateway          # журнал шлюза
docker compose logs -f --tail=50 compute

# проверки цепочки
curl -s http://localhost:8082/health    # обработчик
curl -s http://localhost:8081/health    # шлюз
curl -s http://localhost:8081/chain     # видит ли шлюз обработчик
curl -s -X POST http://localhost:8081/api/process \
     -H "Content-Type: application/json" -d '{"text":"проверка"}'

# внутрь контейнера
docker compose exec gateway sh          # shell в контейнере №1
docker compose exec compute sh
docker compose exec gateway cat /app/app.py     # что реально лежит в образе
docker compose exec gateway env | grep PORT     # переменные окружения контейнера

# сеть
ss -tulpn | grep -E '8081|8082'         # кто слушает порты на хосте
docker inspect pr4_gateway --format '{{.HostConfig.NetworkMode}}'   # → host
```
